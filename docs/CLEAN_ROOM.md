# Clean-room work

Some useful material can't come into this project: leaked source code, leaked symbol files, and research
done by people who had them open while they worked. Its *code* and *names* stay out
([PROVENANCE.md](PROVENANCE.md)). What it shows about the game's files and behaviour can come in, whatever
the material is, through a
[clean-room](https://en.wikipedia.org/wiki/Clean-room_design) process: the knowledge crosses over as a
written description, and the code is written fresh by someone who never saw the original.

**What this does and doesn't cover.** The clean room here is this one path: outside material, read by an
examiner, reaching the project only as specs ("outside research" below means any such material). It does not make the project as a whole a clean-room
reimplementation. A matching decompilation reads the original program: the game's own machine code is the
reference every function is checked against. So the claim the project makes is narrower and should be
worded that way: **no leaked source code is in the repository, nor any code or name taken from it or
from anything written beside it; what examiners learned from such material comes in only as reviewed
specs; you need your own copy of the game.** Don't describe the decompilation itself as "clean room".

**What is not behind the wall.** Anything a contributor holds their own copy of: the game, prototype and
review builds, other games, development kits and manuals, and whatever those discs carry, linker maps
included. Anyone may read those directly, implementers too ([PROVENANCE.md](PROVENANCE.md)). The wall is
for leaked source and leaked symbol files only.

## Other builds the project reads

Other builds are open to any contributor who holds their own copy, on PROVENANCE.md's three conditions:
what is taken is checked against Scarface's code, the build is recorded here, and its files stay out of
the project. To add one, describe it in your pull request the way the entries below do: which build,
whose copy, which file, and what is taken from it.

The 10 July 2003 PS2 prototype
of *The Simpsons: Hit & Run*, a game on the same engine, carries its own linker map on the disc. Since 18
November 2026 the project takes virtual functions' names from that map where the two games' classes line up
([NAMES.md](NAMES.md), `portal/scripts/names_from_shar_map.py`).

* **What is read:** the map file and the prototype's program, from the founder's own copy of the disc. They
  are a build's own by-products, not source code. Neither file is in this repository.
* **What is not:** *Hit & Run*'s source code, which has leaked, is not a source of names: it must not be
  consulted to check, complete or correct a name from the map. It is leaked material: it may be read only by
  an examiner, under the roles below, and that reading goes in the record.
* **What it gives:** names only, each recorded in `reports/names.json` with the class and slot it came
  from. No code, layouts or behaviour are taken from it.

Since 18 November 2026 a second build is read, for one narrow thing. The 5 February 2006 Xbox prototype of
*The Godfather* (another studio's game, another engine) was built with the same Xbox SDK as Scarface and
carries its linker map. Microsoft's library functions, which the linker copies unchanged into every game,
take their names from that map where their bytes are found exactly once in Scarface's program
([NAMES.md](NAMES.md), `portal/scripts/names_from_xdk_map.py`).

* **What is read:** that map and that build's program, from the founder's own copy. Neither file is in this
  repository.
* **What is taken:** the names of Microsoft's library functions only, and which of Scarface's functions are
  library code. Nothing of *The Godfather*'s own code, names or data.

## Roles

* **Examiner.** Reads the outside research and writes a **spec** in `docs/cleanroom/`: what the game's
  files contain and what the game does with them, in their own words. No code, no pseudo-code, no
  names from the research. Names allowed in a spec are the ones this repository already has (from the
  game's own type information and strings) and text stored in the game's files. Every statement must be
  something anyone can check on their own copy of the game. An examiner doesn't implement that spec.
* **Reviewer.** Checks the spec before anyone builds from it: no code, no names that only the outside
  research has (compare every identifier against the repository and against the research's name lists),
  nothing copied word for word. Records the result below.
* **Implementer.** Builds from the spec, the repository and their own copy of the game, and **never opens
  the outside research** (not its code, notes or name lists). If the spec is unclear or wrong, the
  implementer checks the game files or asks the examiner a question in an issue. The answer goes into
  the spec, so the record stays complete.

Anyone can be an examiner, but once you have read the outside research you can't be the implementer
for anything it covers. Say which side you are on in your pull request.
